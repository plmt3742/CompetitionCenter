# 长期可复用设计

> “可复用”指同一套系统能跨届次、跨任期、跨维护者继续用；不是做成多租户 SaaS。
> 本文是验收“真实长期可用”的检查表。

## 1. 复用的五个维度

| 维度 | 问题 | 机制 |
|---|---|---|
| 跨届次 | 下一届能不能不从头建？ | 模板 + 克隆 + 届次滚动 |
| 跨任期 | 换负责人能不能接？ | 岗位包 + 权限到期 + 交接 |
| 跨维护者 | 换开发者能不能改？ | 文档 + ADR + 迁移 + 导出 |
| 跨工具 | 换平台能不能搬？ | 稳定 ID + 标准导出 + 文件校验和 |
| 跨数据 | 历史能不能解释？ | 版本 + 来源 + 审计 |

## 2. 复用资产矩阵

| 资产 | 跨届次 | 跨任期 | 跨维护者 | 载体 |
|---|---|---|---|---|
| 卷宗结构 | 是 | 是 | 是 | 模板版本 |
| 阶段与清单 | 是 | 是 | 是 | 模板快照 |
| 条目类型/标签 | 是 | 是 | 是 | 字典 |
| 岗位职责 | 是 | 是 | 是 | 岗位包 |
| 权限 | 部分 | 是 | 是 | 角色 + 授权到期 |
| 公开页面 | 是 | 是 | 是 | 发布状态 |
| 代码 | 是 | 是 | 是 | 仓库 + ADR |
| 数据 | 按保留 | 是 | 是 | 导出 + 备份 |
| 经验 | 是 | 是 | 是 | 复盘 + 下届建议 |

## 3. 模板库

至少维护五类模板：

1. **赛事卷宗模板**：算法类、开发类；阶段、清单、默认角色。
2. **运营卷宗模板**：招新、总结、物资、合作。
3. **条目模板**：通知、规则、成绩公示、复盘、交接包。
4. **岗位包模板**：职责、周期任务、联系人、坑、权限。
5. **公开页面模板**：赛事详情、通知、成果。

规则：

- 模板版本化；发布后可弃用，不删除历史版本。
- 模板变更不影响已有卷宗；升级需预览与确认。
- 模板里不放真实数据、不放具体年份、不写死人名。
- 每届结束后用复盘决定模板改什么，不临时改。

## 4. 届次滚动

新一届启动时按顺序做：

- [ ] 选模板与版本，创建卷宗；填写年份、届次、负责人。
- [ ] 克隆上一届结构，确认不复制 L3/L4 数据。
- [ ] 更新规则版本、时间线、报名方式。
- [ ] 重新指派阶段负责人；确认权限到期时间。
- [ ] 检查公开端旧内容：哪些保留、哪些下架。
- [ ] 归档上一届；生成赛事交接包。
- [ ] 更新模板与检查清单（只改下一届生效）。

克隆的“携带项”要显式勾选：规则、FAQ、复盘、公开介绍可带；报名、成绩、赛题、评审不带。

## 5. 岗位与人员解耦

- 岗位有稳定 ID 与模板；人只是任职者。
- 任职有任期、范围（全局/组/赛事）与到期时间。
- 权限授予绑定任职，不绑定个人；离任自动提醒回收。
- 交接包从岗位生成，不靠个人整理。
- 关键岗位至少两人可操作（备份负责人）。

离职/毕业检查：账号停用、权限回收、资料转移、交接包签字、公开联系人更新。

## 6. 配置与字典

### 可配置

- 组名与组职责、阶段、条目类型、标签、保留年限、通知模板、公开导航、默认角色。
- 配置由管理员维护，版本化，变更写审计。

### 不可配置

- L1–L4 四级密级与默认拒绝。
- 核心状态机与审计只追加。
- 已发布条目不可原地修改。
- 权限的最小检查顺序。

### 护栏

- 修改模板/字典前预览影响范围。
- 危险配置（降低密级、缩短保留、开放导出）需要二次确认与原因。
- 配置变更不追溯改写历史数据。

## 7. 数据可迁移

- 导出格式：JSON（对象）+ CSV（表格）+ 文件 manifest（路径、校验和、密级）+ schema 版本。
- 每学期做一次全量导出演练；能导入到空环境并抽查 10 条。
- 文件保留原始格式与校验和；不把 PDF 当唯一副本。
- 迁移脚本幂等、可重跑；迁移前自动备份。
- 不依赖单一平台专有数据库格式作为唯一副本。

## 8. 运维可持续

| 周期 | 动作 |
|---|---|
| 每日 | 自动备份元数据；检查失败任务与磁盘 |
| 每周 | 检查收集积压、超期任务、待发布内容 |
| 每月 | 权限与授权到期检查；公开内容抽查 |
| 每学期 | 备份恢复演练；模板复盘；账号清理 |
| 每年 | 保留期清理；导出归档；ADR 与 runbook 复审 |

Runbook 必写：部署、备份、恢复、迁移、回滚、密钥轮换、数据泄露处置、发布错误撤回。

Bus factor 要求：至少两人能部署与恢复；凭据在密码管理器；账号所有权可转移。

## 9. 演进与弃用

- 字段/类型/模板弃用先标记 `deprecated`，保留读取与导出。
- 至少跨一个完整学期再移除；移除前提供迁移脚本。
- 导出 schema 带版本；新版本兼容旧数据读取。
- 破坏性变更写 ADR，说明影响与回滚方案。
- 代码与文档同一提交更新；不允许“代码改了文档没改”。

## 10. 复用验收清单

- [ ] 新一届卷宗 1 天内建好，结构完整。
- [ ] 模板升级不改变历史卷宗内容。
- [ ] 克隆不复制任何 L3/L4 数据。
- [ ] 新任负责人 1 天内靠交接包完成一件真实任务。
- [ ] 新任维护者 1 天内能按 runbook 恢复一份备份。
- [ ] 所有核心对象可导出并在空环境导入。
- [ ] 权限到期自动失效；离任权限被回收。
- [ ] 公开内容与内部条目同源，不复制。
- [ ] 代码、文档、ADR、变更记录一致。
- [ ] 连续两届使用后，模板只需微调，不需要重做流程。

## 11. 反模式

- 把年份、届次、组名硬编码进页面或权限。
- 直接复制上一届文件夹，把报名表和成绩一起带过去。
- 模板原地修改，导致历史无法解释。
- 只有 PDF 导出，没有结构化数据。
- 所有账号与服务器掌握在一个人手里。
- 权限按“组”授予，忽略交叉成员与赛事范围。
- 交接靠聊天记录，没有核对与签字。
- 备份从未恢复过。
- 文档写在个人笔记里，仓库里没有。

## 12. 维护节奏

- **每场赛事**：赛后 14 天归档；生成赛事包；复盘。
- **每学期**：权限复核；备份恢复；模板评审；账号清理。
- **每学年**：换届交接；保留期清理；全量导出；ADR 复审。
- **每次结构变更**：更新文档、文件树、变更记录与 ADR。

## 13. 结论

长期可复用不是靠“功能多”，而是靠：

1. 结构与数据分开（模板 vs 实例）。
2. 人与岗位分开（任职 vs 权限）。
3. 内容与发布分开（条目 vs 公开状态）。
4. 历史与当前分开（版本 vs 生效）。
5. 系统与工具分开（标准导出 vs 平台）。

这五条守住，系统换一届、换一人、换一个技术栈，都能继续用。

# 技术选型标准

## 状态

**未决策。** 本文只记录评估维度、候选方向与待验证问题，不在 P0 拍板。选型结论在 P1 spike 后另写 ADR。

## 原则

1. 单人可维护优先于技术先进。
2. 少依赖优先于功能齐全。
3. 数据可迁移优先于开发效率。
4. 隐私边界清晰优先于自动化。
5. 先用真实赛事验证，再扩展。

## 评估维度

| 维度 | 问题 | 权重 |
|---|---|---|
| 团队技能 | 现有成员会什么？下一任维护者能接手吗？ | 高 |
| 部署条件 | 学院是否给服务器/域名/备案？还是云主机？ | 高 |
| 成本 | 托管、存储、邮件、域名年费 | 中 |
| 隐私 | 数据存放位置、备份、访问控制 | 高 |
| 可维护 | 依赖数量、升级频率、文档 | 高 |
| 可迁移 | 元数据与文件导出难度 | 高 |
| 性能 | 万级条目、几百份文件是否够用 | 中 |
| 生态 | 中文搜索、文件预览、SSO 集成 | 中 |

## 候选方向（仅列举，不代表推荐）

| 方向 | 适合 | 风险 |
|---|---|---|
| TypeScript 全栈（如 Next.js + Postgres） | 一个语言、公开端 SSR/SSG 方便 | 依赖更新快；需要 Node 运维 |
| Python API + 前端框架 | 算法组成员熟悉 Python；易对接 OJ | 两套语言；部署稍复杂 |
| 低代码/多维表格（飞书、Notion 类） | 快速验证流程 | 权限与公开门户弱；锁定风险 |
| 静态站 + 无头 CMS | 对外门户 | 不解决档案与内部事务 |
| 现成档案/DAM 系统改造 | 文件管理 | 赛事模型不合；改造成本高 |

## 待验证 spike

| 编号 | 问题 | 验证方式 | 通过标准 |
|---|---|---|---|
| S-01 | 学院是否提供 SSO | 问学院信息中心/指导老师 | 有明确接口文档或否定结论 |
| S-02 | 服务器/域名/备案 | 同上 | 有可用部署路径或明确外购预算 |
| S-03 | 文件存储规模与备份 | 统计历史资料大小 | 给出容量与备份方案 |
| S-04 | 中文全文检索 | 用真实字段做小样本测试 | 万级条目下结果可接受 |
| S-05 | 公开端静态化/SEO | 做一个赛事详情页原型 | 可缓存、可分享、移动端可读 |
| S-06 | 报名数据回流 | 用现有表单导出 CSV 试导入 | 字段可映射、去重可行 |
| S-07 | OJ 成绩导入 | 取一份脱敏成绩单 | 能生成排名与获奖名单 |

## 决策门槛

满足以下条件才进入选型 ADR：

- S-01、S-02 有结论（哪怕是"没有 SSO，用内部账号"）。
- S-03 有容量量级。
- 至少一个真实赛事的字段与流程跑过纸面演练。
- 维护者能说清"下一任怎么部署与恢复"。

## 已知约束

- 开发环境为 Windows；Node、Python 均可用。
- 维护者为单人，AI 辅助，不能承担重型运维。
- 仓库公开，但运行数据不公开。
- 不引入需要专职 DBA/运维的组件。

## 明确不选

- 需要复杂集群与专职运维的架构。
- 与厂商深度绑定、导出困难的低代码平台作为唯一数据源。
- 自建 OJ/判题。
- 把 AI 模型服务放进核心链路。

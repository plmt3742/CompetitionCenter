# 系统总览

## 范围

系统由两个界面、一组领域模块和一套平台能力组成。当前只定逻辑架构，不选技术栈。

## 逻辑架构

```text
┌──────────────────────────┐        ┌──────────────────────────────┐
│ 公开端 portal             │        │ 内部端 workspace              │
│ 赛事 / 通知 / 成果 / 报名  │        │ 工作台 / 卷宗 / 收集 / 组织 / 交接 │
└────────────┬─────────────┘        └───────────────┬──────────────┘
             │                                      │
             └──────────────────┬───────────────────┘
                                ▼
                 ┌──────────────────────────────┐
                 │ 应用服务 / API                │
                 ├──────────────────────────────┤
                 │ archive      competition     │
                 │ intake       organization    │
                 │ affairs      portal          │
                 │ handover     platform        │
                 └───────┬──────────────┬───────┘
                         │              │
             ┌───────────▼───┐   ┌──────▼────────────┐
             │ 元数据数据库    │   │ 文件对象存储        │
             └───────────────┘   └───────────────────┘
             ┌───────────────┐   ┌───────────────────┐
             │ 搜索索引        │   │ 审计日志            │
             └───────────────┘   └───────────────────┘
```

## 数据流

### 1. 收集到档案

```text
原始资料 → intake（登记，标密级）→ 个人处理（AI/人工）
        → 负责人复核 → archive 条目（版本、来源、文件）
        → 可选：portal 发布（仅 L1）
```

### 2. 赛事到清单

```text
选择模板 → 创建卷宗 → 生成阶段与完整性清单
        → 任务与责任人 → 阶段推进 → 缺件检查 → 收尾归档
```

### 3. 对外发布

```text
L1 条目 + 审校 → 发布 → 公开端读取 → 下架/归档
```

发布是状态变更，不复制内容；公开端永远读同一份条目。

### 4. 交接

```text
岗位/卷宗 → 汇总职责、在办、历史、缺件、联系人
        → 生成交接包 → 双人核对 → 权限转移 → 归档确认
```

## 系统边界

| 外部系统 | 关系 | 说明 |
|---|---|---|
| 学院 SSO | 可选集成 | 若可用，优先复用；否则内部账号 |
| 邮件/公众号 | 通知渠道 | 系统生成内容，人工发布 |
| OJ/评测机 | 对接或导入 | 不自建判题；成绩以导入/链接归档 |
| 报名表单 | 外链或内建 | 首版可外链，数据回流 |
| 个人 AI 工具 | 系统外 | 只登记处理链，不调用 API |
| 对象存储/网盘 | 文件存储 | 需支持校验和与导出 |

## 平台能力

- **身份**：内部成员登录；外部选手/评委按需轻量身份。
- **鉴权**：RBAC + 范围（全局/组/赛事）+ 密级；默认拒绝。
- **搜索**：结构化筛选优先，全文检索后置；结果按密级过滤。
- **审计**：发布、权限变更、删除、导出、越权尝试。
- **通知**：站内为主；邮件可选。
- **备份**：元数据每日、文件每周；恢复演练每学期一次。
- **导出**：元数据 CSV/JSON + 文件 manifest；确保可迁移。

## 非功能要求（草案）

| 维度 | 要求 | 验证 |
|---|---|---|
| 隐私 | L3/L4 默认不可公开；原始资料不入库 | 权限测试、发布抽查 |
| 可用性 | 赛事期间公开端可读；内部端故障不影响已发布内容 | 降级演练 |
| 性能 | 内部检索 < 1s（万级条目）；公开页可缓存 | 压测/实测 |
| 可维护 | 单人可维护；依赖少；升级有记录 | 交接演练 |
| 可迁移 | 全量元数据与文件可导出 | 每学期导出一次 |
| 可访问 | 移动端可完成收集与看板 | 手机实测 |

## 部署形态（逻辑，不选型）

最小可行形态：

- 一个 Web 应用（公开端 + 内部端）。
- 一个关系型数据库（元数据）。
- 一个文件存储（本地或对象存储）。
- 一个搜索能力（先数据库全文，后独立索引）。
- 定时备份任务。

不需要一开始就拆微服务；模块边界在代码内保持清晰即可。

## 关键风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 模块边界模糊，档案与赛事互相依赖 | 中 | 以卷宗为聚合根，赛事模块只管届次与阶段 |
| 权限与密级实现不一致 | 高 | 统一鉴权入口，所有查询强制过滤 |
| 文件存储不可迁移 | 高 | 校验和 + manifest + 定期导出 |
| 公开端与内部端复制内容 | 中 | 发布状态机，单一内容源 |
| 过早拆服务 | 中 | 单体优先，按真实负载再拆 |

## 未决问题

- 搜索是否需要独立引擎。
